# 01 设计思想

## 1. 一句话概括

Hwacha 是一台**解耦的向量取指（decoupled vector-fetch）机器**：它继承 Cray-1 式传统向量机的编程模型和效率，但把所有向量指令从标量控制流中"提升"到一个独立的**向量取指块（vector-fetch block）**中，由一个独立的向量前端去取指、译码和执行。控制处理器只需要发送一个 PC，就可以继续做别的事。

这一决定使得三层解耦成为可能：

1. **控制线程与工作线程解耦**：Rocket 标量核（控制线程）与 Hwacha（工作线程）通过命令队列连接，标量核可以跑在向量单元前面很远。
2. **访存与执行解耦**：向量预取单元（VRU）与向量执行单元（VXU）从同一个向量取指块取指，VRU 提前发出预取。
3. **lane 之间解耦**：多 lane 配置下各 lane 独立步进，不再锁步。

## 2. 问题背景：三种数据并行架构各有缺陷

论文用条件 SAXPY（CSAXPY）作为贯穿例子：

```c
void csaxpy(size_t n, bool cond[], float a, float x[], float y[])
{
  for (size_t i = 0; i < n; ++i)
    if (cond[i])
      y[i] = a*x[i] + y[i];
}
```

| 架构 | 代表 | 主要缺陷 |
|---|---|---|
| Packed-SIMD | SSE/AVX/NEON | 向量宽度硬编码在 opcode 和地址计算里，加宽向量就要加新指令、重新编译；需要额外的尾部（fringe）代码；标量操作数要先 splat 成向量 |
| SIMT | NVIDIA GPU | 每个线程都要做边界检查、各自计算地址，标量操作数（基址、系数 a）在每个线程里都复制一份，寄存器堆利用率低；靠大规模多线程隐藏访存延迟，要在片上保存全部线程状态 |
| 传统向量机 | Cray-1 | 有向量长度寄存器（VLR）和标量支持，代码对硬件向量长度透明、无尾部代码；但向量指令和标量指令混在同一条指令流里，控制处理器每次 stripmine 都要重新取指译码全部向量指令 |
| Vector-thread | Scale、Maven | 把向量算术指令提升到向量取指块，但向量访存指令仍留在标量流；块内允许分支，硬件隐式管理分歧（divergence），且块内不能表达标量操作数和标量计算 |

Hwacha 的立场是：传统向量机的方向是对的，只要配上一个**标量化编译器（scalarizing compiler）**，向量架构可以拥有与 GPU 相同的可编程性，同时更高效、更适合作为编译目标。

## 3. 核心决定：把整个向量块提升出去

与 Maven 只提升算术指令不同，Hwacha v4 把**向量访存、向量算术、向量-标量混合、纯标量指令**全部放进向量取指块。带来的直接收益：

- 控制线程每次 stripmine 只需执行 `vsetvl`、几条 `vmca`、一条 `vf` 和地址簿记，指令数比传统向量机少（CSAXPY 例子中少 15%，向量指令越多节省越多），所以能跑得更靠前，解耦深度更大。
- 向量前端拥有自己的 4 KB 指令缓存，向量块被反复执行时不占用控制核的取指带宽。
- VRU 可以直接扫描向量块，找出所有常量步长访存并提前预取，且这些预取**几乎是非投机的**。

为了让 VRU 的预取非投机，架构上做了一个关键约束：**向量地址寄存器（va0–31）在工作线程中只读**。基址和步长只能由控制线程通过 `vmca` 写入，因此 VRU 在看到 `vf` 时就已经确切知道每条单位步长/常量步长访存会碰哪些地址，不依赖 VXU 的任何执行结果，也不会死锁。

## 4. 六大架构特性

### 4.1 用访存/执行解耦隐藏访存延迟

隐藏延迟的四种手段：静态调度（VLIW）、动态调度（乱序）、预取、多线程（GPU）。GPU 靠多线程，代价是每个等待中的线程要把全部状态留在片上，所以需要巨大的 SRAM 寄存器堆。当地址流事先可知时，预取只需要缓冲预取数据本身，片上状态小得多。Hwacha 采用经典的解耦访存/执行（Smith 1984）思路：VRU 是访存处理器，VXU 是执行处理器，二者从同一个向量块取指，避免了原始 DAE 架构需要两份指令流的复杂性。

### 4.2 用标量化利用操作数一致性

论文第 4 章证明：简单的编译器收敛/方差分析可以把约三分之一的操作静态标量化。Hwacha 提供 64 个**向量共享寄存器（vs0–63）**，向量指令可以直接以 vs 作为源操作数，块内也可以执行读写 vs 的标量算术和标量访存指令。早期向量机（Cray-1、NEC SX）有类似能力，packed-SIMD 必须 splat，AMD GPU 的标量寄存器主要用于分歧管理。

### 4.3 用谓词高效处理控制流

论文第 5 章证明：向量谓词加上**一致性分支（consensual branch）**即可高效处理 if-then-else、循环、函数调用甚至虚函数。Hwacha 提供 16 个谓词寄存器（vp0–15），**所有**向量指令（含 gather/scatter 和 AMO）都可以带谓词并可取反；`vcjal.{all,any}` 在谓词全真/任一真时跳转；`vpop` 用 8 位真值表实现任意三输入逻辑；`vpl`/`vps` 可把谓词溢出到内存。不做硬件分歧栈，分歧管理完全交给编译器。

### 4.4 带可重启异常的虚拟内存

向量块中所有地址都是虚地址，翻译可能失败，因此需要保存/恢复向量单元的微架构状态，让 OS 可以处理缺页并重新调度进程。Hwacha 不做向量寄存器重命名，因此允许多条向量指令部分完成，代价是架构状态更大。方案最接近 DEC Vector VAX：给 OS 一个不透明的状态保存/恢复机制，加上 fence 指令同步向量单元与标量核。

### 4.5 可重构的硬件向量长度

`vsetcfg` 告诉硬件本内核用到多少个 64/32/16 位向量寄存器和谓词寄存器，硬件据此把物理寄存器堆重新划分，得到最大硬件向量长度（HVL）。用的寄存器少，向量就长；用的多，就避免溢出。粒度比 GPU 按 warp 占用率量化细得多，且寄存器数和向量长度都不必是 2 的幂。无论如何配置，HVL 至少为 8。

### 4.6 混合精度

同一个内核里往往同时存在 64 位地址、32 位数据、16 位输入。Hwacha 允许按寄存器配置精度，窄精度元素密集打包在寄存器堆中，功能单元利用子字并行获得 2 倍或 4 倍吞吐。与 packed-SIMD 不同，所有精度下每个向量寄存器的元素数保持一致，因此不同精度的操作可以自然 chaining。详见 `16-mixed-precision.md`。

## 5. 微架构层面的设计原则

- **面向 ASIC 的面积效率**：向量寄存器堆用 4 个 256×128 位的 1R1W 8T SRAM 宏，而不是昂贵的多端口触发器寄存器堆；用操作数锁存器 + systolic 调度模拟多端口。
- **无停顿的 systolic 调度**：微操作（µop）逐 bank、逐周期传递，n 个周期启动后每周期向共享功能单元提供 n 个操作数。
- **非投机的乱序发射窗**：序列器像一个小型乱序发射窗，但没有投机，靠 age 仲裁选择无冒险的操作。
- **变延迟单元完全解耦**：除法、开方、访存把结果写入 per-bank 写队列，序列器异步跟踪退休。
- **直连 L2 而非 L1D**：换取带宽（每 lane 128 位）而牺牲延迟，靠解耦和合并（coalescing）补偿。
- **一切参数化**：lane 数、bank 数、序列器条目、各功能单元流水级数、各队列深度都是 Chisel 参数。

## 6. Hwacha 不是什么

- 它**不实现** RISC-V 标准 V 扩展（RVV）。Hwacha 是非标准的 XHwacha 扩展，工作线程指令为 64 位定长编码。
- 它不是 GPU：没有硬件分歧栈、没有 SFU、没有纹理单元。
- 它不是 packed-SIMD：向量长度对代码透明，同一二进制在 1 lane 和 4 lane 机器上都能以各自的 HVL 正确高效运行。

## 7. 与后续工作的关系

论文第 7.3 节已经预告：Berkeley 团队接下来会定义一个传统向量风格、32 位编码、以 x/f 寄存器作为共享标量寄存器的 RISC-V 标准 V 扩展。这就是后来的 RVV。Hwacha 中关于可重构 VRF、按寄存器配置精度、谓词化一切、解耦访存的经验，都以不同形式进入了 RVV 与后来的 Berkeley 向量机（如 Saturn）。
